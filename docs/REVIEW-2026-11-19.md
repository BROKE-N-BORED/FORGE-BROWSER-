# Forge Browser Review 5: a user pass over v0.13

Date: 2026-11-19. Reviewer: Muse (subagent), driving the shipped
v0.13 tree at ~/workspace/forge-browser-ai/ the way a first-time user
would. REVIEW ONLY: no code was changed in any tree. New findings are
filed in TASK-LIST-2026-11-19.md as R5-01 to R5-07. The 20 open
Review 4 items were re-checked and have their own section below;
they are not re-filed as new findings.

Method: the real window (create_window from the tree) driven under
Qt offscreen at the sandbox's 800x800 screen, plus a local test site
(links, an image, a GET form, a ZIP link, a PDF link, a long page),
a stub Ollama that answers the chat ACTION protocol, a stub SearXNG,
a stub GitHub releases endpoint, a slow HTTP server, and the doorway
driven from a separate process using only the standard library.
53 screenshots are in shots/, numbered to match the areas below.

## What was driven, area by area

### First launch, start page, menus, How to Use

The window opens on the start page with the chat dock on the right,
the brain header reading "Brain: qwen3.5:4b (auto) (answering)" and
"Retrieval: on" against the stub, live RAM stats in the corner, and
the status line "Forge Browser: no accounts, no API keys. Nothing
leaves this machine." All seven menus (File, Edit, View, History,
Bookmarks, Tools, Help) are present with sensible items; Help
carries "Check for updates" and the checkable "Check for updates on
startup". No modal appears at launch and the dock starts scrolled
to the top. Shots: s01-01, s01-03, s09-01.

Two findings live here, both in How to Use (R5-02, R5-03): the
dialog has no Close or OK button anywhere, so a first-time user has
to guess the window X or Esc; and its content is the developer
documentation (the repo tree, the audit lists, "Verify (the #65
contract)", "Research (Item 3)", a "Developer topics" section),
not help written for a user. Shot: s01-04-howto.png. The topic
column also still shows its horizontal scrollbar (R4-15, below).

### Browsing

Address-bar navigation, tab open/close/switch, the local search
results page for word searches, a form submit, and a long page all
work. Back and Forward were proven by clicking the glyph buttons
through a two-page history, and Reload by watching a fresh load
cycle start and finish. One behavior worth naming: the address bar
stays empty on every 127.0.0.1 page, not just the browser's own
pages. The code (app.py, _sync_address, item R3-27) shows this is a
deliberate decision for the browser's own local pages, but the
check matches the whole 127.0.0.1 origin space, so a page on the
user's own local server also shows no address to read or copy.
Filed as an open question at the end, not a defect.

Downloads are the weak spot of the window, and both problems are
carried Review 4 items (R4-01, R4-05, R4-20, R4-10 below): clicking
a download or PDF link saves the file correctly but replaces the
tab with a "Could not reach this page" error page that even names
the page you were on as the one that failed. The Downloads dialog
works (Open, Show in folder, Retry all present) but has no way to
clear finished downloads and no empty-state guidance. Save as PDF
now asks where to save, which is the R4-07 improvement; its done
message still names only the file, not the folder. Shots: s03-01
to s03-04, s01-05-downloads-empty.png, p02-openfile-sample-pdf.png,
p02-openfile-sample-zip.png, p02-openfile-notes-txt.png,
p03-save-as-pdf.png.

### Chat dock

Driven end to end against the stub brain: a search turn approved at
the plan gate, a search turn denied, an open-page turn (it opened
page two in a new tab), a read-this-page turn, the Summarize
button, a slow turn stopped mid-flight, the Brain/Fast/Vision
pickers, and the AI kill switch. The plan gate is a modal box,
"The browser wants to: Search the web for "test site". Allow it?",
with Yes and No buttons; the turn log narrates each phase ("…
searching", "searching took <1s") and the status line counts up
while a turn runs. Stop works during a turn: it is enabled from the
moment a turn starts, and clicking it during a 25-second think left
the status "Stopped after 3s." and a "Stopped." line in the log.
The kill switch works exactly as a user would hope: AI off changes
the header to "AI is off: turn it on below to use chat, tidy
titles, and memory.", disables Send, and AI back on restores the
brain header. Changing the Brain picker to qwen3:1.7b updated the
header to "Brain: qwen3:1.7b (your pick)" at once. Shots:
s06-03-search-turn-done.png, s06-07-slow-turn.png,
s06-08-after-stop.png, s06-09-ai-off.png, p06-watchdog-dialog.png.

Three new findings live here. R5-01 (Medium): clicking Summarize
writes the raw protocol line 'Forge Browser: ACTION {"type":
"summarize"}' into the chat log, where it stays in the saved chat
history across restarts. R5-05 (Low): denying a plan at the gate
leaves no trace in the log; the turn still ends with a normal
"Done" answer, so the user cannot see that the action was skipped
(the search itself correctly did not run). R5-06 (Low): the Vision
picker offers nomic-embed-text, an embedding model that cannot
describe images. Shot: s06-05-summarize-done.png,
s06-04-deny-turn.png.

Two carried items also showed up here: Send with an empty input is
enabled and silently does nothing (R4-12), and with a brain that
never answers, Send and Summarize stay enabled and a sent message
spins at "working: thinking…" with no warning, even though the
header already says "(not answering)" (R4-02). Shot:
s07-02-turn-spinning.png.

### Vault

The full flow works: create a passphrase, add an entry (the list
shows it at once, which is the R4-04 change below), lock, a plain
wrong-passphrase error ("Could not unlock the vault: wrong
passphrase, or the vault file has been changed"), unlock, and a
delete confirm that defaults to No and keeps the entry on No and
removes it on Yes. The locked page still doubles its first
sentence (R4-11): the heading reads "The vault is locked." and the
line under it reads "The vault is locked. Enter the passphrase to
unlock it." Shots: p05-01 to p05-07, p05-05-vault-locked.png.

One robustness note, filed as R5-07 (Low): the add-entry save
crashes with AttributeError at app.py line 3064 (save_entry,
self._vault is None) if it runs while no vault is unlocked. In
this review that state was reachable only by driving a widget on
the dialog's hidden stacked page after a failed "create" attempt
on an existing vault; no path through the visible UI was found.
The traceback is in probe6b.log.

### Bookmarks and history

The star button bookmarks the current page with a plain status
message ("Bookmarked: Test Site Page Two") and toggles it off
again on a second press, and the Bookmarks menu, once opened,
lists the bookmarks in the menu itself plus an "All Bookmarks…"
viewer. Ctrl+D is the carried problem (R4-03): it is completely
dead, with no feedback of any kind, until the Bookmarks menu has
been opened once in the session; from then on it works perfectly,
including the toggle. The refusal wordings were captured live:
the start page gets "The start page can't be bookmarked." and a
local file page gets the generic "Only web pages can be
bookmarked." with no file-specific reason (R4-16, R4-17 below).

The History dialog opens, has a search filter, and its empty state
is plain and helpful ("No visits recorded yet. Browse a page and
it shows up here."). It stayed empty throughout this drive because
history recording excludes 127.0.0.1 visits by design (titles.py,
record_visit); whether real web visits record could not be
verified in the sandbox (see Environment notes). Shots:
p04a-01-after-star.png, p04b-01-history.png.

The navigation toolbar's tooltips are a small new finding (R5-04,
Low): Back, Forward, Reload, and Home report their tooltips as the
glyphs themselves ("←", "→", "⟳", "⌂"), so hovering a button
never tells a new user what it does in words.

### Updates (the v0.12 surface)

Driven against the stub GitHub endpoint. A manual check with the
stub at the current version reports "You have the newest version
(0.13)." in a plain dialog. With the stub offering 0.14 and the
startup toggle on, launching pops the ask dialog: "Forge Browser
0.14 is out. You have 0.13. Update now? The download is checked
against its published checksum before it installs, and your vault,
memory, and history are …" with Yes and No. With the toggle off,
launching against the same newer stub shows no dialog at all after
8 seconds. The toggle persists correctly in settings
(check_updates flips between "1" and "0"). Shots: u-dlg-1.png,
u-dlg-2.png, s08-03-startup-silent.png.

The install path was driven against a throwaway installed copy,
never the tree: Yes on the ask popup downloaded the fake 0.14
release, and the installed copy's version file read 0.14
afterwards with the previous copy kept beside it as
forge-browser-app.old, which proves the checksum-verified download
and the safe swap ran. The install step itself (the new copy's
install.sh) outlasted the review's 420-second watch window in this
sandbox; the app allows it an hour. The restart prompt at the end
of a successful install was therefore not observed. The throwaway
copy was deleted after the drive.

### The doorway (the v0.13 surface)

Driven the way Fyrn will use it: the doorway started from the
command line as its own process, and a separate client process
using only the standard library's urllib talked to it.

* Startup: it took the default port 18787 and wrote the actual
  port to ~/.forge/doorway/port. A second doorway started while
  the first was running took port 18788 and rewrote the port file.
* Open task: POST /task {"type":"open","url":…} returned a task id
  with status "queued". Polling GET /task/<id> showed the phase
  move from "opening http://127.0.0.1:8971/index.html" to "reading
  the page" to "done", with current_url set throughout. The result
  carried the right final_url, clean page Markdown (heading,
  links, "[image: A red square]"), a markdown_path whose page.md
  held the full text, and a screenshot_path whose shot.png is a
  real 1920x1080 PNG that visibly shows the rendered test page.
* Queueing: two open tasks submitted back to back ran one at a
  time in order; the second sat at state "queued", phase
  "waiting", until the first finished, then completed.
* Research task: {"type":"research","query":"test site"} moved
  through "searching" to "reading the page" and finished with the
  best stub result opened and its Markdown returned.
* GET /tasks listed all four tasks newest first.
* Errors were plain and correct, every one: a non-http(s) URL got
  400 "open only takes http(s) pages, refused 'ftp://example.com/x'";
  a missing URL got 400 "an open task needs a url"; an empty query
  got 400 "a research task needs a non-empty query"; an unknown id
  got 404 "no task with that id"; the wrong method on a route got
  405. A local URL sent to a doorway started WITHOUT the
  allow-local setting got a 400 that names all three ways to allow
  it (the flag, the command line switch, the env var).
* Shutdown: SIGTERM stopped the doorway cleanly, printed "Doorway
  stopped.", and removed the port file.

One observation, not a finding: in the doorway's screenshot the
test page's red PNG image appears as its alt text rather than as a
painted image, while the same image renders in the browser window.
This may be capture timing in the headless engine; it is recorded
here so a future drive can check it deliberately.

### Window sizes

at 360px; at 800x560 the page view still gets 434px. At the

## Environment notes

* The sandbox screen is 800x800, so the first-launch window is
  the designed clamp to 798x720, not the 1240x720 default; sizes
  were verified by explicit resize instead.
* The sandbox's TLS path breaks WebEngine's direct HTTPS (the
  handshake to example.org failed through the sandbox proxy), so
  real-web page loads and real-web history recording could not be
  verified here. The browser's own error page for that failure
  rendered correctly.
* Chat, search, and update endpoints were stubs on 127.0.0.1 by
  design; token-per-second figures in the chat log are stub
  artifacts.
* Window size persists between runs, which is why later scenarios
  opened at 760x620.
* Driving the tree imports it, which writes Python __pycache__
  files under the tree; no source file was created, edited, or
  deleted, and the pre-review ~/.forge state was restored whole
  after the drive.
* No EPERM write burst occurred during this review's drives.

## What could not be driven, and why

* Real-web browsing and history recording: sandbox TLS (above).
* The end of the update install (restart prompt): the install
  step outlasted the 420-second watch in this sandbox; the app
  allows it 3600 seconds, and the swap itself was verified.
* The real run_app splash path behind R4-18: the drive uses
  create_window in-process, which has no splash.
* Voice input ("Hold to talk"): no microphone in the sandbox.
* A real Ollama brain: the stub answers the same ACTION protocol;
  answer quality with real models is not a UI question.
