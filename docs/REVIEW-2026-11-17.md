# Forge Browser v0.11 - Review 4 (user pass, 2026-11-17)

Reviewer drove the real v0.11 app as a first-time user, in the sandbox,
through the driver's scenarios plus 18 targeted probes. 153 screenshots
in `shots/`. No code was changed. This report covers the first
reviewer's 20 screenshots (launch, splash, print, new window,
fullscreen, open file) and this pass's scenarios and probes.

Method: Qt offscreen, fb-venv, one app instance at a time. Local test
site only for pages (real websites are unreachable from WebEngine in
this sandbox). Two reviewers' work is combined here; where the first
reviewer's screenshot suggested a defect, a probe re-checked it with a
longer wait before it was listed. Several suggestions turned out to be
timing artifacts and are listed under "Checked and cleared", not as
findings.

Counts: 1 High, 6 Medium, 11 Low, 2 Missing feature. 20 findings.

Environment notes (read before judging severity):
- A real Ollama IS running in this sandbox (16 models, incl.
  qwen3.5:4b). It is heavily loaded by other work, and free RAM was
  139-505 MB across runs. Turn timeouts here are load artifacts, but
  the timeout VALUES and the UX around them are still reviewable.
  A stub Ollama (fakechat probe) proved the chat path itself works:
  a turn completed in under a second with a rendered reply.
- WebEngine cannot reach real websites in this sandbox (the sandbox
  proxy is not used by WebEngine's network stack). Real-page tabs
  and web downloads are UNTESTED, not broken.
- Back/forward after a link click fails in this sandbox, exactly as
  in Review 3. Review 3's minimal repro proved `back()` after a JS
  `.click()` navigation fails even in a bare QWebEngineView with no
  Forge Browser code, while `back()` after two programmatic `load()`
  calls works. This pass confirmed the `load()` path still works
  (back-after-loads probe). Link-click history needs a real display
  or Joshua's PC.
- Launch took 2.3s to 25.1s across runs (sandbox load variance).
- Paths shown as `home-sXX/...` in screenshots are relative only
  because the test homes were relative paths. On a real machine HOME
  is absolute, so this is NOT reported as a finding.
- The sandbox OOM killer took 3 app processes during this pass
  (Batch F, probes3). Those deaths are sandbox memory pressure, not
  product crashes. No crash and no data loss was observed in any
  scenario that ran to completion.
- Fake-Ollama lesson: `chat.py` freezes OLLAMA_URL at import time
  (`from .media import OLLAMA_URL`), so a probe that starts a stub
  server in-process and sets FORGE_OLLAMA_URL afterwards still talks
  to the real Ollama. The stub only works when the variable is set in
  the caller environment before launch. The driver's s13_fakeollama
  has this flaw on top of its port conflict (real Ollama holds
  11434); it was skipped and the fakechat probe (port 11436, caller
  env) was used instead.

## HIGH

### R4-01 - Open File on a PDF or ZIP downloads it and shows a misleading "Could not reach this page" error tab
Severity: High.

What happens: File > Open File on sample.pdf downloads the file
(status bar: "Downloaded sample.pdf to .../Downloads/sample.pdf")
and the new tab shows the dark "Could not reach this page" error
page ("Forge Browser could not open ..."). Same for sample.zip.
The file exists, it downloaded fine, and the tab says it cannot be
reached. Two tabs titled "Could not reach this page" pile up. The
address bar is EMPTY on these error pages.

Scenario: first reviewer, s19_openfile. Screenshots:
19-open-pdf.png, 19-open-zip.png. HTML, TXT, and PNG open
correctly in tabs (19-open-index-html.png, 19-open-notes-txt.png,
19-open-red-png.png).

Code cause: `_open_file` (app.py:1562-1572) loads any picked file
through `new_tab` with no type check. Its docstring claims
"WebEngine renders HTML, text, images, and PDF natively". That is
wrong for this PySide6 build, whose WebEngine ships no PDF viewer
plugin, so the PDF falls through to the download manager. The
navigation is then consumed by the download, `_on_load_finished`
fires with ok=False, and the friendly error page is shown
(app.py:1136-1145). The download path and the error page do not
know about each other.

What a fix needs: Open File must not show an error page for a file
that downloaded. Either render PDFs through the engine room's own
PDF text extractor (files.py already extracts PDF text) or, for
types that download, show a plain "Downloaded <name> to <folder>"
page in the tab instead of the error page. The error page should
only appear when the load genuinely failed. The `_open_file`
docstring's PDF claim needs correcting either way.

## MEDIUM

### R4-02 - Send stays enabled while the brain is "(not answering)", so a turn spins the full 120s timeout before failing
Severity: Medium.

What happens: with the brain header showing "(not answering)",
Send and Summarize stay enabled. Starting a turn spins "working:
thinking..." for the whole first-read timeout (FIRST_READ_SECONDS
= 120, chat.py:100) before failing. s05b watched one to 102s still
spinning; s13b watched one to 120s; the send-watch-long probe
watched the full arc: thinking at 30s, 60s, 90s, then "Failed after
121s." with the log line "Forge Browser: The chat brain
(qwen3.5:4b) did not answer: timed out". The failure itself is
graceful and clear, and names the brain and the cause. The defect
is the missing fail-fast: the app already knows the brain is not
answering, and lets the user start a turn that cannot succeed for
two minutes. Compare the Ollama-down state, where Send/Summarize
correctly disable (s23c, 23c-brain-60s.png). After the failure,
Send is enabled again at once, so the user can start another doomed
turn immediately (P13-send-watch-long.png). Small side note: the
thinking timer is unreliable under load (68s shown at 90s wall in
s05b; 120s shown at 90s wall in send-watch-long).

Scenario: s05_chat, s05b_sendwatch, s13b_realchat,
send-watch-long probe. Screenshots: 13b-real-chat-done.png,
P13-send-watch-long.png.

Code cause: the turn buttons disable only for the ollama-down and
no-models states (app.py:3121-3128), not for "(not answering)".
The first-read timeout is chat.py:100 (120s).

What a fix needs: treat "(not answering)" like the Ollama-down
state for Send/Summarize (disable them, or fail fast with the plain
"the brain is not answering" message instead of starting a 120s
turn). Keep the graceful 121s failure as the backstop for a brain
that stops answering mid-turn.

### R4-03 - Ctrl+D is dead until the Bookmarks menu has been opened once
Severity: Medium.

What happens: in a fresh window, Ctrl+D does nothing at all: no
bookmark, no message. Proved twice: on a file page (ctrl-d probe:
bookmarks 0 before, 0 after, status unchanged) and on the http
search results page (ctrl-d-http probe: same). After the Bookmarks
menu is opened once, Ctrl+D fires (ctrl-d-after-menu probe: the
status line then shows the bookmark refusal). The star toolbar
button works from the start. Every piece of guidance tells the
user to press Ctrl+D: the bookmarks empty state ("press Ctrl+D to
add one"), the Bookmarks menu ("Bookmark This Page Ctrl+D"), and
the star tooltip ("Bookmark this page (Ctrl+D)"). A first-time user
following the guidance gets silence.

Scenario: ctrl-d, ctrl-d-http, ctrl-d-after-menu probes.
Screenshots: P11-ctrl-d.png, P17-ctrl-d-http.png,
P19-ctrl-d-after-menu.png.

Code cause: `_bookmark_action` is created once with the Ctrl+D
shortcut (app.py:1525-1530) but is added to the menu ONLY inside
`_rebuild_bookmarks_menu` (app.py:1874), which runs on the menu's
aboutToShow signal. A QAction shortcut only fires while the action
belongs to a visible widget, so before the menu is ever opened the
shortcut has nowhere to fire from. The G-UX3 comment claims the
once-created action fixed "Ctrl+D was dead until the menu opened";
it fixed the duplication, not the dead-until-opened part.

What a fix needs: add the action to the window at creation
(`self.addAction(self._bookmark_action)`) or add it to the menu
once at build time, so the shortcut fires from launch. Keep the
single-action rebuild (no duplication).

### R4-04 - The vault list does not refresh after adding an entry
Severity: Medium.

What happens: create a vault, add a login, save it: the entry IS
saved (vault list_entries shows it), but the list in the dialog
stays empty. The user sees an empty vault and would think the add
failed. The entry only appears after Lock vault and unlock again.
Proved by widget state, not just pixels: vault-add-count probe,
list count 0 after Save with the entry present in list_entries.
P9-vault-after-add.png is byte-identical to
P9-vault-after-create.png (both empty); P9-vault-reunlocked.png
shows "example.org (joshua)". No traceback; the dialog stays open
correctly throughout (see "Checked and cleared").

Scenario: vault-behavior, vault-add-count probes. Screenshots:
P9-vault-after-add.png, P9-vault-after-create.png,
P9-vault-reunlocked.png, P18-vault-after-add-count.png.

Code cause: not pinned to a line. `do_add` calls `refresh()` after
`form.exec()` returns accepted (app.py:2853), and `refresh()`
rebuilds the list from `list_entries()`, which holds the new entry.
Yet the widget stays empty until the unlock path runs the same
`refresh()`. The builder needs to find why the add path's refresh
does not land (ordering with the nested form exec loop is the
prime suspect).

What a fix needs: after a successful add, the list must show the
new entry at once, with nothing selected (Delete stays disabled
per R3-11). Same check for delete: the removed entry must vanish
at once.

### R4-05 - Clicking a download link can blank the tab while the download succeeds
Severity: Medium.

What happens: s22 clicked the sample.zip link on the test page.
The download completed ("Downloaded sample.zip to
.../Downloads/sample.zip"), but the tab went blank white with the
title "Could not reach this page" (22-after-download.png). The
address bar kept the index.html URL. s10 ran the IDENTICAL click
and the tab stayed on the test page (10-download-started.png).
Same actions, different tab outcome: the download navigation
sometimes consumes the tab and sometimes leaves it alone. The
user loses the page they were reading and must reload it.

Scenario: s22_indicator vs s10_downloads. Screenshots:
22-after-download.png, 10-download-started.png.

Code cause: same family as R4-01. When WebEngine hands a
navigation to the download manager, the tab's load can fail and
`_on_load_finished(ok=False)` shows the error page (app.py:1136).
Whether the tab survives is a race between the download takeover
and the load failure path.

What a fix needs: a navigation that becomes a download must never
replace the tab's page with an error page. Keep the previous page
in the tab (as s10 shows is possible) and let the status line and
the Downloads dialog report the download.

### R4-06 - The load progress bar strands at a stale value when a navigation does not complete normally
Severity: Medium.

What happens: the status-bar progress bar appears on loadStarted
and hides only on loadFinished (app.py:1127-1138). When a
navigation never finishes, the bar sits visible at a stale value
forever: 20% after the s22 download completed
(22-after-download.png), 0% with 12 blank tabs
(21-many-tabs.png, 21-after-jump.png), 0% on the reopened tab
while its load stalled (P2-reopen-6s.png). The user sees a phantom
progress bar that never moves and never goes away.

Scenario: s22_indicator, s21_overflow, reopen probe. Screenshots:
22-after-download.png, 21-many-tabs.png, P2-reopen-6s.png.

Code cause: app.py:1127-1138. `_on_load_started` shows the bar,
`_on_load_finished` hides it, and nothing else ever hides it. A
download takeover, a stalled load, or a tab switch away from a
loading view leaves it visible.

What a fix needs: hide the bar when the current view changes, when
a download takes over the navigation, and on a watchdog (a load
that reports no progress for a while is stalled; hide the bar
rather than strand it). The bar must never outlive the load it
belongs to.

## MISSING FEATURE

### R4-19 - No stop-loading control
Severity: Missing feature.

What happens: there is no Stop button and no way to stop a page
load in progress. The toolbar has back, forward, reload, home.
Reload never becomes Stop during a load, and nothing in the menus
stops one. Several loads stalled for 20s or more in this pass
(s20 start page, s21 start page) with no recourse but closing the
tab. A browser needs a stop control for exactly the slow-load case
this sandbox produces constantly.

Scenario: s20_saveas, s21_overflow (20s load timeouts).

What a fix needs: a Stop control during loads (toolbar button
that swaps Reload for Stop while loading, or Esc to stop the
current tab's load), wired to the view's stop().
