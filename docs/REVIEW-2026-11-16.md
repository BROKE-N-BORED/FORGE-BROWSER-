# Forge Browser v0.10 - User Review (Review 3)

Date: 2026-11-16. Reviewer: the agent, driving the real app as a first-time
user under the offscreen Qt platform in the sandbox. REVIEW ONLY: no code
was changed, nothing was pushed, nothing was fixed.

Method: the shipped v0.10 tree was copied to
`~/workspace/forge-browser-ai-review3/` and driven scenario by scenario
with `review-driver.py` (launch, start page, address bar, tabs, chat dock,
menus, bookmarks, history, memory, vault, downloads, How to Use, window
sizes, real-Ollama chat, settings/research/voice/summarize/cards), plus
focused probes (`vault-probe.py`, `minsize-probe.py`, `bigsize-probe.py`,
`summarize-probe.py`, `minimal-back-test*.py`). Every screenshot in
`shots/` was read. Findings are numbered R3-01 to R3-33.

Environment notes (read before judging severity):
- A real Ollama IS running in this sandbox (14 models, incl. qwen3.5:4b
  and qwen3:0.6b). It is heavily loaded by other work, and free RAM was
  ~181 MB at check time. Turn timeouts here are load artifacts, but the
  timeout VALUES and the UX around them are still reviewable.
- WebEngine cannot reach real websites in this sandbox (the sandbox proxy
  is not used by WebEngine's network stack). Real-page tabs, web
  downloads, link-click navigation and back/forward after link clicks are
  UNTESTED, not broken. A minimal repro proved `back()` after a JS
  `.click()` navigation fails even in a bare QWebEngineView with no Forge
  Browser code, while `back()` after two programmatic `load()` calls
  works. Link-click history needs a real display or Joshua's PC.
- Launch took 3.9s to 58.8s across runs (sandbox load variance). The
  spread itself is environmental; the lack of any startup indicator is
  a finding (R3-26).
- Paths shown as `home-sXX/...` in screenshots are relative only because
  the test homes were relative paths. On a real machine HOME is absolute,
  so this is NOT reported as a finding.

## HIGH

### R3-01 - The chat dock has no scroll area: the window cannot fit a 768px-tall screen, and the seat descriptions clip
Severity: High. Rule hit: U5 (fit 1366x768).

What happens: the dock panel's content sets the window's minimum height.
Measured with `minsize-probe.py`: window minimumSizeHint 373x793, dock
minimumSizeHint 240x714, dock widget min hint 214x689. `resize(1240, 720)`
leaves the window at 1240x793. On a 1366x768 screen the window is 25px
taller than the screen. The advertised default size 1240x720 is
impossible with the dock open. With the dock closed the minimum height
drops to 115 and resizing works, so the dock is the sole cause.

Same root cause clips the seat descriptions: at 793px window height the
layout crushes the Brain/Fast/Vision description labels to about 1.5
lines, the second line cut mid-glyph ("Brain: answers questions and
drives the / browser"). At 1080px height the same labels render in full,
so the clipping is height-driven, not width-driven: with no scroll area,
a short window squeezes the labels instead of scrolling.

Evidence: `minsize-probe.py` output; `shots/01-launch-10s.png`,
`shots/12-size-640x480.png` (clipped); `shots/12-big-1920-settled.png`
(full descriptions at 1080px). Code: `forge/browser/app.py` dock build
(~line 2618+); there is no QScrollArea anywhere in app.py. The labels do
set `setWordWrap(True)` (app.py:3058), which is not enough on its own.

### R3-02 - The "Models and AI" button is unreadable (white on white)
Severity: High.

What happens: the section toggle in the dock renders as a white/light
rectangle with white/light text. It is a checkable QToolButton, checked
by default (app.py:3017-3021). The stylesheet sets only its text color
(`QLabel, QCheckBox, QToolButton { color: #e8e4da; }`, app.py:83) and has
no QToolButton background or `:checked` rule, so the checked state paints
light while the text stays cream. Present in every dock screenshot.

Evidence: `shots/01-launch-10s.png`, `shots/02-startpage.png`,
`shots/zoom-dock.png`, `shots/12-big-1920-settled.png` (still white at
1080px, so this is not the height issue).

### R3-03 - After a failed load, the address bar shows a giant data: URL instead of the address that failed
Severity: High.

What happens: when a page fails to load, the app shows its friendly
"Could not reach this page" page, but the address bar fills with the full
percent-encoded `data:text/html;charset=UTF-8,...` blob. The user cannot
see, edit, or copy the address they typed. Root cause: `_on_load_finished`
calls `view.setHtml(load_failed_html(url))`, and Qt implements setHtml as
a data: URL load, so `view.url()` IS the data: URL. The comment in
`_sync_address` ("a setHtml page leaves the bar as it was") is false for
WebEngine: the comment's premise is wrong, not just the code.

Evidence: `shots/03-example-org.png`, `shots/03-bad-url.png`,
`shots/03-bare-domain.png` (address bar tail reads
`address%2C or check your connection%2C then try again.%3C%2Fp%3E...`).
The error page itself is good plain words; only the address bar is wrong.

### R3-04 - The brain header looks healthy for ~40 seconds before "(not answering)" appears
Severity: High.

What happens: with a brain that does not answer, the header reads
`Brain: qwen3.5:4b (auto)` with no qualifier for over half a minute while
the answer check runs (`check_model_answers`, 30s timeout, chat.py:329).
Observed: header unchanged at 2/5/10/15/20/30s, "(not answering)" only at
40s. There is no "(checking...)" state, so the user sees a healthy brain
and may send a message into a dead end.

Evidence: `shots/01b-brain-40s.png` (s01b_brainwatch).

### R3-05 - No fix button when the brain is "(not answering)"
Severity: High.

What happens: the G-UX5 one-click fix buttons ("Start Ollama" etc.) only
appear for the `ollama-down` and `no-models` brain states. A model that
is installed but does not answer gets no remedy at all: the header just
says "(not answering)" and the user is left to guess.

Evidence: `shots/01b-brain-40s.png`.

### R3-06 - The brain silently re-picks to a different model between launches, with no explanation
Severity: High.

What happens: `pick_chat_model_with_reason` (chat.py:236+) drops the size
guide to 1 GB when free RAM is under 1 GB, so the 3.32 GB qwen3.5:4b
becomes oversize and the fallback loop picks qwen3:0.6b with reason
"fallback" and no note explaining why. Across review runs, some homes
picked `qwen3.5:4b (auto)` and others picked `qwen3:0.6b (fallback)` with
nothing but RAM load differing. The user sees the brain change and has no
way to know why or that RAM was the reason.

Evidence: `shots/04-twelve-tabs.png` (header: `Brain: qwen3:0.6b
(fallback) (not answering)`), `shots/13b-real-chat-done.png`.

### R3-07 - Chat fails after 10 seconds; Summarize can hang for up to 4 minutes; Stop cannot interrupt a stalled read
Severity: High.

What happens: the streaming brain call uses a 10s per-read timeout
(chat.py:676: `read_timeout = 10 if on_chunk is not None else 240`). On a
loaded 2-core CPU box, a cold model load plus first token can exceed 10s:
a real turn against the real Ollama with qwen3:0.6b failed at 10s
("The chat brain (qwen3:0.6b) did not answer: timed out"). The failure
itself is graceful and honest; the VALUE is the problem. A first turn
after Ollama restarts, or any turn under load, can fail even though the
model would have answered at 15s.

Summarize goes the other way: on a multi-chunk page the map calls run
without `on_chunk` (`summarize.py:148`: `stream_map = on_chunk if
len(chunks) == 1 else None`), so each gets the 240s timeout. Observed:
"Summarize" on a 60-paragraph local page still showed "working:
summarizing... 19s" at 20s with no end in sight. And Stop cannot help:
`cancel()` only lands between steps (chat.py), so during a stalled HTTP
read the Stop button does nothing visible for up to 240s, even though the
K1 comment says Stop works during a summarize.

Evidence: `shots/13b-real-chat-done.png`, `summarize-probe.py` output,
chat.py:676, summarize.py:148.

### R3-21 - The debug report says "PySide6: not installed" while running on PySide6 6.12

same on Joshua's PC (install.sh installs the same 6.12 packages). The
rest of the report is good plain words (OS, Python, RAM, disk, services,
recent actions, errors, log tail).

Evidence: `home-s11/.forge/logs/debug-report-forge-browser-20261116-224728.txt`;
fb-venv site-packages listing (`pyside6_essentials-6.12.0.dist-info`,
no `PySide6-*.dist-info`).

### R3-26 - No splash or loading indicator during startup
Severity: Low.

### R3-27 - The address bar is deliberately emptied on local pages
Severity: Low. A design choice, flagged as a UX question, not a bug.

served page (search results, history, memory pages). Worth a deliberate
decision either way.

Evidence: `shots/03b-search-results.png` (empty address bar on the
search results page).

## MISSING FEATURES (things Firefox/Chrome do that this does not)

### R3-28 - No Print
No print path anywhere in app.py (no QPrinter, no printToPdf). A browser
without Print cannot print a page or save one as PDF.

### R3-29 - No New Window
There is no New Window menu item or action. One window only.

### R3-30 - No Fullscreen (F11)
No fullscreen action. View menu has zoom + Chat Dock only.

### R3-31 - No "Open file" (Ctrl+O)
No way to open a local file from the menus. Local files only open by
typing a file:// path in the address bar.

### R3-32 - No per-download "Save as" choice
Downloads go straight to ~/Downloads (or the Settings folder) with no
dialog. There is no "always ask where to save" option and no way to pick
a different folder for one download.

### R3-33 - No tab overflow menu
With 13 tabs the tab bar scrolls with arrows; there is no dropdown to see
or jump to a tab by name. (Tabs ARE movable: `setMovable(True)`,
app.py:614. Tab bar has a custom context menu.)

## NOT PRODUCT BUGS (sandbox/environment artifacts)

- Real websites failing to load in WebEngine tabs: the sandbox proxy is
  not used by WebEngine's network stack. The engine-room search (urllib +
  proxy env) works fine.
- Launch-time variance (3.9s to 58.8s) and "(not answering)" states:
  sandbox load (another thread's llama-server + test suites, ~181 MB free
  RAM at check time).
- Relative paths in dialogs ("home-s10/Downloads/..."): the test homes
  were relative paths; on a real machine HOME is absolute.
- The 1920x1080 narrow-column shot (`shots/12-size-1920x1080.png`):
  resize lag; the settled shot shows the page filling correctly.

## UNTESTED (with reasons)

- Real websites in WebEngine tabs: sandbox proxy blocks WebEngine
  network. Covers real-page rendering, link-click navigation, back/forward
  after link clicks, web downloads, form filling, login flows, CAPTCHA
  handoff (no real site to trigger one).
- A successful chat turn with a real answering brain: both real-Ollama
  attempts timed out under sandbox load. Covers the 3-action turn flow,
  plan-gate UI, research jobs, compare, brief refresh, and cards producing
  real output.
- Voice with a real microphone: no mic in the sandbox; only the no-mic
  error path was tested.
- Vision seat describing a real image: needs an answering brain to drive
  it.
- First-run engine download (~1 GB via install.sh): not run.
- Real Mint double-click install and app-menu launch: no desktop session
  in the sandbox.
- Kitesurf engine live: still never driven (known from v0.8).
- Session restore across restarts with real tabs: only dock state was
  tested.
- The debug log file's day-to-day content: only the generated report was
  read; the running log had one line in the test homes.
